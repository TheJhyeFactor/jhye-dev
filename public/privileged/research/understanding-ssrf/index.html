Understanding SSRF Through a Small Lab Application

An innocent-looking URL preview feature and a closer look at where server-side requests are allowed to go.

Written by Jhye
#web#ssrf#networking

This is fictional sample content for the notebook. It describes a lab scenario, not a real finding or a project Jhye has released.

A URL preview is an easy feature to underestimate. The browser supplies an address, the server fetches it, and a title comes back. But the server’s network view may be very different from the browser’s.

This fictional example uses a local preview service and a second test endpoint inside the same disposable lab. There is no production target or real internal data.

A different network perspective

When a server follows a caller-provided URL, the caller influences a request originating from the server. If destinations are unrestricted, the request could reach resources the caller cannot access directly.

In the lab, a harmless internal endpoint returns a fixed marker. Seeing that marker in a preview response demonstrates reachability to that one endpoint. It does not establish reachability to every internal service.

Validation needs a policy

Checking that a string starts with https:// is not a destination policy. Hostnames can resolve to private addresses. Redirects can point somewhere different. Names can have more than one address.

A narrow allowlist of approved upstream services is easier to reason about than unrestricted fetching. If a feature needs arbitrary public URLs, destination handling becomes a much more careful part of the design.

StageQuestion to answer
URL parsingIs the scheme allowed, and is the URL unambiguous?
DNS resolutionAre all candidate addresses allowed by the policy?
ConnectionIs the connection bound to a validated destination?
RedirectIs every hop checked with the same policy?
ResponseAre size, type, and time bounded?

Bound the request

The lab’s first improvement is replacing arbitrary URLs with a small set of known upstreams. It also disables redirects, caps response size, and sets a timeout.

The reserved .invalid domains are placeholders, not working services. This snippet illustrates selecting a destination from trusted configuration; it is not a complete fetch implementation.

Verify the boundary

Test the approved flow and the rejection flow. Include redirects, unexpected address families, malformed URLs, oversized responses, and timeouts where the chosen implementation supports them.

The lesson is straightforward: a network request is a capability. A preview feature needs to decide exactly how much of that capability a caller should control.
