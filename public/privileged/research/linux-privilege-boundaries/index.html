Finding Privilege Escalation Paths on Linux

Looking at permissions, service configuration, and the small assumptions that become interesting at a privilege boundary.

Written by Jhye
#linux#permissions#security
Demo write-up

This is fictional sample content for the notebook. It describes a lab scenario, not a real finding or a project Jhye has released.

On this page
Map the boundaryCheck assumptionsReduce the privilegeKeep the evidence

This fictional lab starts with a maintenance service that runs as root and loads a helper script from a shared directory. The useful question is not just “what runs as root?” It’s “who can change what root will run?”

The environment is a disposable local VM. The example is about understanding and fixing a configuration mistake.

Map the boundary

A service file specifies the command that runs. The command loads a script. The script’s parent directory is writable by a less privileged group. That creates a chain from ordinary file access to code executed with elevated privileges.

Inspecting the entire path is important. A script can have restrictive permissions while an attacker-writable parent directory permits replacement of the file.

namei displays permissions along the path. stat records ownership and mode on the current file. The unit definition shows what the service manager intends to execute.

Check assumptions

These observations are a starting point. The actual service may be constrained by namespaces, a read-only filesystem, an alternative mount, or a mandatory access control policy. Check the effective environment before describing an exploitable path.

ComponentIntended ownerWritable by ordinary user?
Service unitrootNo
Helper directoryrootNo
Helper scriptrootNo
Runtime output directoryService accountOnly as required
↳ Scope the conclusion

A writable file is not automatically an escalation. Verify that the privileged process reaches it and that the effective execution environment allows the change to matter.

Reduce the privilege

The best fix might be removing root from the equation. If the maintenance task only needs access to a specific data directory, give a dedicated service account narrowly scoped access to that directory.

For the fictional lab, the remediation has two parts: remove write access to the helper path for ordinary users, and run the service under a dedicated account. Review any group membership that would undermine those changes.

Keep the evidence

Record the unit configuration, ownership chain, group membership, and relevant runtime constraints. After making the change, repeat the same inspection and verify the service still completes its intended task.

A permission fix that silently breaks the maintenance job is incomplete. A functioning job with a trustworthy execution path is the outcome to aim for.
