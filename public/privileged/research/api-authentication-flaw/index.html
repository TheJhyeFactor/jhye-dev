Breaking Down a Simple API Authentication Flaw

A valid token isn’t the whole story. Following a single request across an API’s trust boundary to see what was missing.

Written by Jhye
#api#authentication#web

There’s a small but important gap between knowing who someone is and knowing what they’re allowed to see. This fictional lab example explores that gap in a deliberately simplified API.

The interesting part isn’t a clever payload. It’s an assumption: once a request has a valid token, the rest of the request must be fine.

↳ The lab setup

The application, accounts, and requests in this entry are fictional. The API runs on localhost with two test users and seeded, non-sensitive data.

The first request

The lab has a profile endpoint at /api/users/:id. Alice can sign in and load her own profile. The browser sends a bearer token, and the server checks its signature and expiry before handling the request.

That request returns Alice’s profile. So far, the behavior makes sense. But what connects the alice in the path to the authenticated subject in the token?

Following the trust boundary

Here’s the intentionally incomplete handler. The authentication middleware has already populated req.user, but the route does not use it when choosing a record.

The server trusts a caller-controlled path parameter as the authority for selecting an account. A valid session is required, but it can select someone else’s record. This is a broken object-level authorization scenario.

A useful way to inspect this is to make the same request as two different users, then change only the resource identifier. Keep the rest of the request fixed so the result has a clear cause.

A controlled proof of concept

This test stays entirely inside the lab. Both accounts belong to the tester. The token is an environment variable, and the output is synthetic profile data.

In the vulnerable version, Alice receives Bob’s synthetic profile. The patched version rejects the request with 403 Forbidden. A 200 alone is not evidence of exposure: the returned fields and account identity need to be inspected too.

What the finding means

In this example, the exposed fields are a display name and email address. The impact is cross-account access to those fields. There is no demonstrated ability to change accounts, become an administrator, or execute code.

That distinction matters. The impact should follow the observed behavior, not the most dramatic interpretation of the bug class.

The exact fix depends on the resource model. An account endpoint might allow only the owner. A shared workspace could instead require membership and a specific permission. In either case, the server needs to make the authorization decision.

Closing the gap

For this small lab, enforce ownership before querying and returning the record. Token subjects and database identifiers should use a consistent canonical representation.

Then test the policy in both directions. Check owner access, non-owner access, missing sessions, invalid tokens, and records that do not exist. If the product intentionally conceals resource existence, use a consistent response policy for forbidden and missing records.

The question I’d keep in the notebook: where does identity become permission? Looking for that transition is more useful than treating the presence of authentication middleware as the end of the investigation.
